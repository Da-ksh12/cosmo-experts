# Model evaluation and release control (Phase 3)

How models and AI components are evaluated here, what has actually been measured, and the rules that decide whether any model may answer a patient. Code: `backend/app/ai/{evaluation,lifecycle,gates}`,
`backend/app/training/trainer.py` (gates), `backend/eval/`. Tests: `test_model_lifecycle.py`, `test_ai_evaluation.py`, `test_ai_gates.py`.

**Phase 5 update (2026-10-20):** five more research models exist (two phone-photo lesion probes, one skin-condition probe, two dermoscopy probes); the gates and their thresholds are unchanged, every model fails at least one, and none is approved or active ([PHASE_5_TRAINING_REPORT.md](PHASE_5_TRAINING_REPORT.md)). The text below describes the Phase 3 state.

**Today no model is approved, none is active for any patient-facing task, and none could pass the gates on the evidence that exists.** The only learned models in the registry are four research models
for lesion classification (below); the local language model fails its gates. Everything patient-facing that works today is rule-based, retrieval-based or classical image analysis.

## 1. Evidence classes (stamped on every report)

| Class | Meaning | Used for |
|---|---|---|
| `synthetic_fixture` | inputs generated by this project (rendered pages, synthesised speech, written questions, fixture models) | proves a mechanism works; says nothing about real use |
| `simulated_degradation` | real inputs with faults added by code | quality checks |
| `public_research_dataset` | real data from a published dataset, licence recorded | research models (PAD-UFES-20) |
| `real_world_clinical` | data from the intended clinical setting | **none exists in this repository** |

A report with `real_world_evidence: false` is never presented as clinical validation. Gates live in one place and are reported, not edited: image models `trainer.GATES`; language models `ai/gates.py`.

## 2. Evaluation runners and where their records are

| Runner | What it measures | Record |
|---|---|---|
| `scripts/evaluate_model.py` (`ai/evaluation/models.py`) | a registered image model on its held-out split: per-class sensitivity/specificity, macro-F1 and balanced accuracy with bootstrap intervals, confusion matrix, calibration (ECE), out-of-distribution, subgroups from dataset metadata, paired comparison, baseline comparison, release gates recomputed, and whether it reproduces its own card | `docs/eval/vision_lesion_research_test.json` |
| `eval/quality_v2_eval.py` | photo quality rules on real photographs: false-flag rate on val/test, detection of simulated faults | `docs/eval/quality_v2.json` |
| `eval/doc_extraction_eval.py` | lab-result extraction on rendered synthetic reports (digital and degraded scans); re-run on `docpipe-2.0.0`, which caught a defect that the unit tests had missed (MEDICAL_DOCUMENT_INTELLIGENCE.md section 3) | `docs/eval/doc_extraction.json` |
| `eval/medication_eval.py` | prescription-line parsing: precision/recall per component, false fills, ambiguity flags, span correctness; development and held-out sets, held-out first run kept | `docs/eval/medication_parser.json` |
| `eval/kb_retrieval_eval.py` | passage retrieval over approved knowledge and out-of-scope detection; threshold chosen on development queries, scored once on held-out queries | `docs/eval/kb_retrieval.json` |
| `eval/agent_eval.py` | action choice, permission denials, steering text, cross-user leakage, citation support | `docs/eval/agent.json` |
| `eval/voice_eval.py` | speech recognition on synthetic English speech, silence, spoken-text fidelity, Hindi/Hinglish fact preservation | `docs/eval/voice.json` |
| `eval/llm_eval.py` | grounded answers by the local language model | `docs/eval/llm_qwen2.5-1.5b-instruct-q4_k_m.json` |

Each report carries the code revision, configuration hash, dataset identity (and licence), environment and notes. Where a set was examined and the system changed in response, the earlier first-run
figure is kept beside the later one and the set is marked as no longer independent.

## 3. The research models that exist

PAD-UFES-20 (CC BY 4.0), test split of 325 images from 194 patients, mostly Fitzpatrick 1-3. Two ResNet18 models and two DINOv2 linear probes (`docs/eval/vision_lesion_research_test.json`):

| Model | Macro-F1 (95% interval) | Balanced accuracy | Accuracy |
|---|---|---|---|
| ResNet18 (two registered copies) | 0.502 (0.429-0.576) | 0.505 | 0.637 |
| DINOv2 probe (two registered copies) | 0.558 (0.471-0.630) | 0.576 | 0.615 |

The best majority-class/baseline macro-F1 is 0.515. The paired difference between the two families is not distinguishable from zero (macro-F1 -0.056, interval -0.143 to +0.022). For the first ResNet18
the release gates **fail**: 4 near-duplicate test images, macro-F1 below the best baseline, no CI support for improvement, melanoma has 7 test images, BCC sensitivity 0.67, SCC sensitivity 0.30,
8 test images in Fitzpatrick 4-6 (need 50), out-of-distribution AUROC 0.27 (need 0.9). Passed: licence recorded, test size, calibration (ECE 0.076), robustness and subgroup tables present.
All four reproduce their own model cards. They are `research_only`, administrator-only, and labelled as not a diagnosis wherever shown.

## 4. The lifecycle (`ai/lifecycle.py`)

```
imported ─┐
experimental ─► evaluation_pending ─► review_pending ─► approved ─► active ─► rolled_back
                    └► evaluation_failed ◄┘                │         └► approved   (deactivated or superseded; kept as the known-good fallback)
                                                   any non-active state ► deprecated (final)
```

State lives in the model's record; every change is an **append-only** event (`model_events`: who, when, from, to, detail; UPDATE and DELETE are refused in SQLite by trigger and in PostgreSQL by
privileges, and the migration tool copies the table) and an audit entry. `GET /api/admin/models/{id}/lifecycle` shows state, allowed next states, the gates, the approval record, the history, when
the model was serving and whether its file still verifies.

**Moving forward**
* *Evaluate* (`POST /admin/models/{id}/evaluate`): the gates are run on the model's recorded evidence. Pass → `review_pending`; fail → `evaluation_failed` with every failed gate listed. An imported model
  has no evidence, so it fails until it has been evaluated.
* *Approve* (`POST /admin/models/{id}/approval`): the five release requirements (held-out evaluation, subgroup evaluation, clinical sign-off, intended use, regulatory review) must all be met, the
  gates must pass, and **the clinical sign-off must name a verified clinician** (`clinical_signoff_by`; an administrator's tick-box is no longer enough). Otherwise the record says exactly what is
  missing and nothing moves.
* *Activate* (`POST /admin/models/{id}/deploy`): only an `approved` model, and only if its file exists and matches its recorded checksum, its intended use, limitations, dataset reference, evaluation
  and approval are recorded, and no clinical issue is open. The previous active model stays `approved` as the known-good fallback. Every refusal is an event.

**Taking a model away**
* *Rollback* (`POST /admin/tasks/{task}/rollback`) goes to the most recent known-good model **whose file still verifies**, or to none; models whose file fails are skipped and reported. The model rolled
  back from becomes `rolled_back` (it cannot be switched back on without being re-evaluated) and **keeps its record and its file**.
* *Deactivate* removes the active model without replacing it: the capability becomes unavailable.
* If the active model is missing, damaged, deprecated or not approved the capability reports **unavailable with the reason**; nothing else is substituted. Research models stay research-only.

**A rollback is technical, not clinical.** It changes which model answers from now on. It does not change, correct or withdraw anything already shown; results name the model that produced them and
that model's record stays. If a model's output may have been clinically wrong, report a *clinical issue* (`POST /admin/models/{id}/clinical-issue`): it does not change what is serving, it blocks
(re-)activation until closed, and `GET /admin/models/{id}/exposure` lists the periods the model was serving so that a clinician can review what it produced then.

**Automatic rollback** exists but is **off** (`COSMO_MODEL_AUTO_ROLLBACK=1` turns it on). It acts only on signals that need no ground truth: the model file failing its checksum (immediate), or - over
at least 50 runs in the last hour - a failure rate whose 95% interval *lower bound* is at least 0.20, counting only the model's own errors and timeouts (never abstentions, rejected input or a busy service).
Without the switch the monitor only recommends (`GET /admin/tasks/{task}/monitor`). Quality drift, disagreement with clinicians or user complaints are deliberately not triggers: they cannot be judged
reliably here.

## 5. Language models in patient-facing roles (`ai/gates.py`)

Required: configured + an evaluation record for that exact model meeting every gate + a recorded administrator approval naming it. The gates (fixed before any result was read): at least 100
questions; JSON validity ≥0.99; claim support before verification ≥0.90; correct after verification ≥0.80; correct source ≥0.80; wrongly answered unanswerable ≤5%; zero injection leaks. For
classification of requests: at least 100 scenarios, tool-selection accuracy ≥0.95, zero permission violations, injection successes, cross-user leaks and unsupported citations.
**Qwen2.5-1.5B** (34 questions): claim support 0.394, answerable correct 0.20, 2 of 6 unanswerable wrongly answered, correct source 0.40 - it fails and is off. `COSMO_ASSISTANT_MODE=llm` alone
does not enable it. Its per-request state is reset before every generation so one person's prompt is never reused for another's.

## 6. What this does not do

* No model is approved or active; the clinic's regulatory and clinical review has not happened, and these gates are the minimum evidence asked for, not a substitute for it.
* The synthetic evaluations (agent, voice, retrieval, medication, document) show mechanisms working on inputs the author wrote; they are not evidence about real use.
* There is no sign-off workflow beyond naming a verified clinician in the approval request, no four-eyes rule between trainer and approver, and no automatic notification of an open clinical issue.
* The monitor keeps recent outcomes in memory (per process); a restart empties it.
